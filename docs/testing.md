# Testing 99.99%

This is the source of truth for test commands, what the suites cover and how CI runs them.
Use Node 22 and install with `npm ci` separately in `frontend/` and `backend/`.
Tests use browser-local saves, Supertest and an in-memory PGlite database; no production database or API key is needed.

## Commands

| Directory | Command | Purpose |
| --- | --- | --- |
| Both packages | `npm run lint` / `npm run typecheck` | Static checks |
| Both packages | `npm test` | Unit and integration tests |
| Both packages | `npm run test:coverage` | Tests plus text, HTML and JSON coverage |
| Frontend | `npm run balance` | Scripted strategies across twelve seeds |
| Frontend | `npx playwright install chromium` | Install the browser once per machine |
| Frontend | `npm run test:e2e` | Build and test real desktop/touch browser journeys |
| Frontend | `npm run test:e2e:ui` | Debug browser tests interactively using an existing build |
| Backend | `npm run db:generate` | Verify schema and generated migrations agree |

On Linux CI, use `npx playwright install --with-deps chromium` for browser and system dependencies.
For interactive tests rebuild with `npm run build` after changing application code.
Preview runs on port 4175 by default (override with `PLAYWRIGHT_PORT` when another checkout is active); a reused local server must serve the current build.

Locally, `npm run test:e2e` runs the whole suite on one worker.

## Browser journey conventions

Browser contexts are isolated. Advanced scenarios use engine-generated states in the normal localStorage save envelope before boot; decisions then happen through visible controls. Journeys that inspect the room check a working WebGL context; the `withoutRoom` fixture skips rendering for journeys that only exercise other UI. All journeys fail on unhandled browser errors. Scaling/instance-selection journeys retain the real scene. Playwright's clock drives incident timers without arbitrary waits.

Journeys that need exact game seconds opt in with the `installClock` fixture before navigation. `advanceCampaignStep(page, { seconds })` runs that many seconds through Run/Pause; use `resumeClock: false` when the caller deliberately keeps virtual time frozen. Scene, walking and audio journeys otherwise retain native browser clocks.

When Chapter 0 is setup for another journey, `completeTutorial` bounds its real lessons to 180 seconds and adds only their measured duration to that journey's test budget. The journey keeps its original remaining budget and assertion timeouts. Seed a completed-tutorial save when the case only exercises an existing company; dedicated tutorial journeys still walk the full guide.

A timed batch acknowledges a Scaling or Data Strategy completion through the existing journey handler, then explicitly clicks Run for its remaining seconds. It finishes paused; dismissing a completion dialog outside a timed batch also leaves the player paused.

- The Opening room-inspection journey keeps native scene frames, selects 2x through the public speed menu and waits for the built-in first-incident pause at game second 6.
- Manual spike planning keeps the virtual clock paused between decisions so moving scene labels and purchase cards settle for interaction. It explicitly renders a newly installed rack while physical time stays paused. The room-control journey checks its installed capacity, routing, pending actions and costs against an engine-generated configuration. A separate journey starts from that verified configuration and drives the announced wave with controlled ticks, retaining the original wave-test budget and gameplay assertions.
- Opening prevention also freezes scene time while choosing purchases, then resumes it for reload checks.

Graphics quality, opening responses, missing-furniture recovery, mode switching and the shared-controls tooltip journey start from engine-generated companies with completed tutorial profiles. Dedicated pointer, keyboard and touch tutorial journeys and the fresh-guest full campaign still complete the real guide. Finance explanation checks start at their own saved lesson and use the real Finance dialog after finishing the remaining lessons. Scaling has separate database-headroom, installation and recovery cases; installation asserts the full engine-generated pending configuration used by recovery, including the room inspection input. Only horizontal installation draws the room; both recovery paths retain measured reports and paused reload checks.

Panel-only journeys for accounts, chapters, finances, prevention and reliability, plus the locked-control tooltip, manual spike survival, write-heavy spike evidence and the touch final scorecard, skip the scene with the existing `withoutRoom` fixture. Their controls, persistence and error assertions still run in Chromium. Equipment selection, walkthrough inspections, camera, floor, walking, graphics and scene-loading journeys keep real WebGL. The six exhaustive growth-order balance checks each have their own Node test file, preserving all 192 peak/duration/order combinations while allowing Vitest to distribute the CPU work. `npm run balance` includes those files as well as the original strategies. In CI, they run in a separate required job without coverage instrumentation; the coverage job excludes only the six exhaustive files. Local `npm run test:coverage` still includes everything.

## CI

The existing required `frontend` job gates `frontend-checks` (static checks and Vitest coverage), `frontend-balance` (all balance strategies and exhaustive bounds), and all ten `frontend-browser` shards (production builds and desktop/mobile browser journeys). These jobs run in parallel. The gate explicitly fails if any dependency fails, is cancelled or is skipped, so branch protection still requires all frontend checks without changing its configuration. Browser shards use `fail-fast: false` to retain diagnostics from every shard. The required `backend` job runs static checks, Vitest coverage and migration consistency. Failed browser tests retain screenshots and traces; CI uploads coverage and browser reports for 14 days. Inspect a shard's downloaded report with `npx playwright show-report` or `npx playwright show-trace <trace.zip>` in `frontend/`.

Browser journeys run one worker per runner to avoid competing software WebGL renderers. CI distributes the full suite across ten runners with `node scripts/browser-shards.mjs 1/10` through `10/10`; the workflow derives the total from its matrix size. The script discovers the current desktop and mobile tests, then places the longest estimated tests on the least-loaded runner. It rejects duplicate test names and includes newly added tests with a conservative 30-second estimate. The estimates in `frontend/e2e/browser-durations.json` affect distribution only; they never filter out tests or change timeouts. Check the plan without running browsers with `node scripts/browser-shards.mjs 1/10 --list`.

Each CI shard builds the same commit independently and uploads its own HTML report, screenshots, traces and `test-results/browser-timings.json` as `browser-results-1` through `browser-results-10`. The [container trial](https://github.com/CS3216-Final-Project/99.9-Percent/actions/runs/39107511656) measured 26-43s just initializing the image, with 52-70s before tests, against 44-55s before tests in the baseline. It was rejected in favor of the hosted Ubuntu runner, a Chromium headless-shell-only install and a browser cache keyed by the installed Playwright version instead of the entire npm lockfile. Linux system dependencies are still installed on every runner. Refresh estimates from all ten JSON reports from the same CI run with `node scripts/browser-shards.mjs --record <report1.json> ... <report10.json>`. Prefer CI timings to local timings because software rendering costs differ by machine. Recording uses only a single clean passing attempt; failed, skipped or retried cases keep the conservative fallback until measured cleanly, and no tests are removed from the discovered suite. CI rejects flaky tests even if a retry passes.

Coverage is a baseline report, with no arbitrary global percentage gate. Frontend reports instrument `src/sim`, `src/game` and `src/lib`, excluding test helpers. They do not measure visual components or aggregate browser coverage. Backend reports include all `src` files, so entrypoints and live database paths may remain uncovered. Add targeted assertions for changed risks rather than chasing a total percentage.

### Duration budget

Aim for **at most 60 seconds per required PR CI job**, including each browser runner. Measure from job start to completion, including checkout, dependency and browser setup, builds, tests, and report uploads. Report queue time separately.

When a job exceeds this budget, profile its slowest tests and setup steps. Optimize fixtures and rendering, move suitable checks into faster unit or integration tests, split long journeys at meaningful boundaries, and rebalance runners using measured durations. Preserve meaningful gameplay, persistence, recovery and failure coverage and all required checks. Keep assertion timeouts based on the behavior being tested; the one-minute goal is not a blanket test timeout.

For performance changes, report before/after GitHub timings for the slowest browser runner and other affected jobs, plus failures, skipped checks and remaining budget overruns. Record an overrun and its bottleneck while working toward the target.

The target is currently unmet. In the [18 October 2026 baseline run](https://github.com/CS3216-Final-Project/99.9-Percent/actions/runs/39104888320), the slowest browser runner took 10m 35s (9m 42s in browser journeys), frontend checks took 1m 40s, and balance took 1m 49s. Browser jobs waited about 24 seconds before starting; queue time is excluded from these job durations. All 142 browser tests passed without retries or skips. Chapter 0 setup alone cost 160s in mode switching and 162s in the missing-furniture journey.

## Accounts and cloud saves

Google OIDC, email and password accounts and optional account-owned snapshots are implemented and tested against mocked provider exchange and isolated PGlite. Outstanding live checks are in [AUTHENTICATION.md](AUTHENTICATION.md#outstanding-acceptance). The automated suite covers:

- **API:** mock Google code exchange/token validation; reject invalid/replayed callbacks, expired/revoked sessions and CSRF; verify two-account save isolation and revision conflicts. Email accounts: salted scrypt hashes, normalised addresses, duplicate registration refused without changing the password, the same answer for a wrong password and an unknown email, session rotation, the 15-minute lock after ten wrong passwords, other origins refused and no Google merge.
- **Database:** additive account/session/attempt/run migrations and constraints with PGlite. Actual Neon HTTP connectivity remains an isolated deployment acceptance check.
- **Browser:** Google cancellation, email sign-in after a wrong password and a refused duplicate account, session restoration/sign-out, explicit Save to cloud, conflict choice in Menu, Saves, another account's save left alone, loading a cloud save in a fresh browser, the offline Account dialog on touch, the landing page's `?signin=1` link opening the Account dialog for a guest and nothing for a signed-in player, and preserved legacy keys. Stub provider responses for repeatable CI.
- **Home screen:** both mode cards on every visit in Guided-first order, each showing its saved game. Challenge Mode is locked with a disabled unlock button until the first five Guided Mode chapters are complete; once unlocked a Guided Mode run in progress can switch to Challenge Mode and back without losing either save. Guided Mode's card replays its walkthrough on the same company once it is done, from either mode's home screen. Analytics runs by default; the analytics notice appears only while the choice is undecided and persists either OK or Opt out (React tests; the analytics browser journey covers OK). A browser with Do Not Track or Global Privacy Control on never starts analytics, even after an acceptance, and its leftover analytics data is cleared (unit tests).
