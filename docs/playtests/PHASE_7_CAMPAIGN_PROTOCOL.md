# Phase 7 combined-campaign playtest protocol

Prepared 11 October 2026. Sessions, live deployment and human acceptance: **NOT TESTED**. Do not contact participants or deploy as part of this preparation.

Use one recorded build of the continuous guest campaign, `combined-campaign` v1 / `combined-pool` v1, default final target 50,000 registered users. Record the actual URL/commit/build, seed and configuration. A dev/unrecorded build does not establish release evidence. Use returning testers and some fresh players where time allows; distinguish recruited from organic participation.

## Session procedure

1. Obtain consent and record anonymous participant/session IDs, familiarity, recruitment source and build/seed. Export existing browser evidence before choosing a new company; do not silently erase another run.
2. Let the participant use the normal public controls. Do not prescribe a purchase sequence or explain the database/cache/failover solution. Observe spontaneous continuation before asking about it.
3. Record each stage and combined round: first inspection, actual investments/routes, workload predictions, incidents, recovery, acknowledgement, traffic limiting, rejection and cash constraints. Record exact facilitator intervention in the existing Menu observer tools.
4. Include prevention, failure, quit and technical interruption; do not discard unsuccessful sessions. Record active and wall durations separately from physical steps. Missing answers remain missing.
5. After completion, allow scorecard, architecture, history and nine-node technology inspection. Observe an actual new-company choice and subsequent gameplay decision before classifying voluntary replay. A reset alone is insufficient.
6. Ask enjoyment (1–5) before coaching. Then ask: Did this feel like one company? Which later decision differed from Opening? Did workload, delay, cash or surviving capacity change your choice? Was any technology always necessary or useless? Why did the run end? Was complexity and duration manageable? What would you change next run?
7. Export the existing session/campaign record, including linked scorecard, run evidence and source context. Download does not delete the archive. Record technical storage failures and unknown historical timing; never treat unknown values as zero.

## Observer sheet

| Field | Record |
| --- | --- |
| Participant / session / run | Anonymous IDs; actual company and session link |
| Build / URL / seed / scenario / target | Actual tested identity and saved pool order |
| Prior familiarity / recruitment | Fresh or returning; recruited / organic / unspecified |
| Company continuity | Did the player notice earlier investments and costs? |
| Strategy | Purchases/routing/controller/reliability decisions; classify afterward |
| Stage / round timestamps | Entry, pressure, incident, recovery, review, final acknowledgement |
| Timing | Physical step, active time and wall time separately |
| Business consequences | Actual spending, limiting, rejected demand, cash and failed requests |
| Comprehension | Predictions, causal explanations, confusion and blockers |
| Help | Exact hint and facilitator intervention, including none/unknown |
| Outcome | Completion / failure / quit / technical interruption |
| Enjoyment | 1–5 before explanation, or missing |
| Continuation / replay | Spontaneous versus prompted; actual new-run decision |
| Usability | Desktop/mobile, keyboard/focus/touch, screen-reader/device limitations |
| Export | Filename and linked run/session evidence; storage failure if any |

## Acceptance review

Compare actual strategy diversity and identify any universal purchase sequence or technology that never affects a decision. Do not equate automated completion with fun, learning, voluntary continuation or a duration target. Report failures and missing responses alongside completions. Maintenance/deployment risk and auth/cloud are deferred. This protocol prepares Phase 7 observations; it does not begin Phase 8's formal evaluation.
