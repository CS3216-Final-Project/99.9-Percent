# Stay Online — Phase 6 observer protocol

Status: preparation only. Deployment and human sessions NOT TESTED. Arrange approximately five participants separately on one recorded build and scenario version; do not contact participants as part of implementation.

Record participant/session ID, prior familiarity, recruited/organic source, build/commit, scenario versions, initial company/routing/cash/research, active/wall timings and exported local evidence. Include failures, quits, technical interruptions and missing answers. Record exact facilitator assistance and optional hints, never infer them.

Before coaching ask what happens when one application stops processing and whether installed capacity guarantees service. Observe first evidence inspected, ownership/prerequisite interpretation, preparation/response, detection versus actual health, pending delays, spare routing and spending. Do not prescribe a purchase sequence. Use the same inherited-company setup for manual and prepared sufficient/insufficient-capacity comparisons where appropriate.

Observe: explicit Stay Online entry → optional tree/research/preparation → Start reliability test → actual failure → inspection/detection/routing → manual/automatic response → measured incident report if one occurs → restoration and stable management → reliability outcome → explicit acknowledgement → paused reload.

Collect enjoyment 1–5 before explanations. Ask:

1. How does capacity differ from reliability?
2. What did Health Checks change, and what did they not change?
3. When did the spare receive traffic?
4. Did failover create capacity? Why might service still overload?
5. How did failover differ from autoscaling/provisioning?
6. Which cost or rejected-demand trade-off did your company accept?

Record spontaneous replay/future-test interest before prompting. Export session context and linked campaign trace; retain unexported records. Report actual outcomes, not assumed learning or duration. This is preparation; Phase 8 owns full learning evaluation.
